# egui-snarl spike: a scratch canvas and an adopt recommendation

> Milestone E0 of `dev-docs/37-gpu-node-models/plan.md` builds a scratch canvas on egui-snarl 0.12 inside the Editor tab, behind a new `snarl-spike` feature that is off by default.
> Every item of the milestone works: the persistent `Snarl` per body, the id map, `Move` diffs, the red 500 stroke, framing, the hover popup, square corners, nested region frames and the web build.
> A graph of 320 nodes and 560 wires holds the display's refresh rate at 6 ms of frame CPU natively and 8 ms in a release build in Chrome.
> Reading the source and testing it found one real gap, that selection cannot be set from outside, and four smaller traps with workarounds, one of them a panic that E1's undo has to guard against.
> The recommendation is to adopt egui-snarl 0.12.0 from crates.io for E1, and to fork only if E1 decides that pasted nodes or a Select all have to start selected.

## State before

`37-node-editor` at `bad936b` had no node editor code.
`design.md` §12 took several claims about egui-snarl from a critic's report and marked them as unverified until this spike.

## What was done

### The scratch canvas

`ui/editor/scratch.rs` is throwaway code that E1 replaces.
The Editor tab shows a Scratch canvas checkbox when the feature is on, and the canvas takes the place of the code view.
A body is a document of nodes keyed by a Henad node id, with a `Snarl<NodeView>` kept in step.
The viewer queues every gesture as a `ScratchCommand`, and the commands run after `SnarlWidget::show` on both sides.
Readouts beside the canvas print the transform, the selection, the regions, the command log, the timings and the screen position of each pin, so the inspection server can read them.

Two toggles, Hold shift and Hold command, write `InputState::modifiers` before the canvas draws.
The inspection server needs them, as "Driving the canvas through the egui MCP server" below explains.

`src/tests/scratch_canvas.rs` holds 36 tests that run the canvas on a headless `egui::Context` with synthetic input.
They pin traps 1 to 4 and 8 and the table rows below whose evidence names a test, so a version bump that changes those fails a test.
Traps 5 to 7 and the rows citing only MCP, screenshots or source have no test.

### Findings on each item

Claims from `design.md` §12 checked against egui-snarl 0.12.0's source, and against the running canvas where marked.

### Traps found

1. **Selection cannot be set from outside.** `SnarlState` and the `SelectedNodes` type are private, and only a read is public (`get_selected_nodes`). This confirms `design.md`. A plain click selects nothing on its own: selection needs shift, and shift with a drag draws a rectangle (`a_plain_click_selects_nothing`). The modifier write under "Plain-click selection" below reaches plain click on the published crate. Pasted nodes cannot start selected, and neither can a Select all, and those two have no workaround.
2. **A structural gesture bypasses the viewer.** A command-drag from a socket calls `snarl.drop_inputs` or `snarl.drop_outputs` directly (`src/ui.rs:1509` and `:1669`, the only direct wire edits outside the viewer's default methods). After each `show` the editor has to compare the `Snarl`'s wires with the document and emit a `Disconnect` for any it lost (`lost_wires`). `a_command_drag_from_an_input_drops_its_wire_without_a_viewer_callback` and the running app cover the input side, and the output side goes through the same comparison untested.
3. **An input takes many wires.** `Snarl::connect` accepts a second wire into one input. The `Connect` command replaces the wire the input holds.
4. **The default header blocks a drag by the title.** `show_header` defaults to `ui.label`, a selectable label that takes the press. A node drags by its title only with `Label::selectable(false)`. `a_node_drags_by_its_title` passes with it and fails without it.
5. **The first transform can be far off.** `SnarlState::initial` fits node positions to the canvas rectangle of its first frame, and a tab opening narrow gave a scale of 0.2. E1 should frame the body itself on opening. The transform lives in egui's temporary memory and does not survive a restart, so `[editor]` has to hold a view if a view is to persist.
6. **The dropped wire disappears while its menu is open.** `new_wires()` returns nothing in menu mode, so the wire is not drawn. This is cosmetic.
7. **No culling.** Every node is laid out each frame wherever the view is. Draw time at scale 1.0 with most of the graph off screen equals draw time with all of it visible. The figures below show this does not matter at the sizes the plan expects.
8. **Removing a node with a wire in flight panics.** `SnarlState` keeps the pins of a wire being dragged, and `src/ui.rs:1333` and `:1352` index that frame's pin maps with them. After `remove_node` takes such a pin's node away, the next `show` panics with "no entry found for key" and ends the process. See "The in-flight wire guard" below.

### The in-flight wire guard

The panic needs a wire in flight whose pins sit on the removed node.
The pinned tests are `removing_the_node_of_an_output_wire_in_flight_panics` and `removing_the_node_of_an_input_wire_in_flight_panics`.
The far end of a command-drag counts too (`removing_the_far_node_of_a_command_dragged_wire_panics`).
Removing any other node during the drag is safe, and the wire still connects (`removing_another_node_during_a_wire_drag_keeps_the_wire`).
From reading the source, a node that loses the socket under the wire through its `inputs` or `outputs` count reaches the same lookup.
This was not run.

The scratch canvas does not reach the panic, since its only `remove_node` runs from menu commands and pressing the secondary button cancels a wire (`src/ui.rs:1229`).
E1's snapshot undo can, because a keyboard undo needs no pointer.

E1 takes one of two guards, and whether a wire is live cannot be read from outside, as `SnarlState` is private.

- **Hold document edits while the primary button is down, and run them after `show`.** A wire only starts on a primary drag and `show` ends it on the release frame. The order matters: the release frame already reports the button as up, so an edit before `show` on that frame still panics (`an_edit_before_show_on_the_release_frame_panics`). `an_edit_held_until_the_button_is_up_and_run_after_show_survives_a_wire` covers the working order. This is the recommended guard, since the editor already runs commands after `show` and it keeps the selection.
- **Change the canvas id for that rebuild.** The new id starts with no wire, and the gesture ends with no connection (`a_new_canvas_id_drops_the_wire_in_flight`). It also drops the transform and the selection.

The dropped-wire menu holds its pins as well.
Removing the node while the menu is open does not panic in egui-snarl (`removing_the_node_of_a_wire_held_by_its_dropped_menu_survives`), since `new_wires()` returns nothing in menu mode.
The pins still reach `show_dropped_wire_menu`, and the scratch viewer's `snarl[pin.node]` would panic if the menu's button were pressed after that removal.
That comes from reading the code and was not run.
E1's viewer should use `snarl.get_node`, or hold edits while that menu is open.

### Plain-click selection

Plain click is reachable on the published crate, with no fork.
Before `show`, on a frame where `primary_released()` and `could_any_button_be_click()` hold and no real modifier is held, write shift and command to `InputState::modifiers`.
Restore them after `show`.
`draw_with_plain_click` in the tests holds the code.

| Gesture with the write | Result | Test |
|---|---|---|
| Click node A, then node B | `[A]`, then `[B]`, the second click replacing the first | `a_modifier_write_makes_a_plain_click_select` |
| Real shift-click after that | Adds to the selection | `a_modifier_write_makes_a_plain_click_select` |
| Click the background | Deselects through `src/ui.rs:1241`. Without the write the selection stays. | `a_background_click_deselects_only_with_the_modifier_write` |
| Drag an unselected node | Moves it and leaves the selection | `a_modifier_write_leaves_a_node_drag_as_a_move` |
| Drag a wire | Connects | `a_modifier_write_leaves_a_wire_drag_connecting` |
| Double-click the background, two frames between the clicks | Centres the graph | `a_modifier_write_leaves_a_background_double_click_centring` |
| Double-click the background, second press on the frame after the first release | Does not centre, while the same input centres with no write | `a_modifier_write_loses_a_double_click_whose_second_press_follows_at_once` |

The last row needs a press one frame after a release, which a person at 60 Hz or above is unlikely to produce.
Its cause was not confirmed, and the rectangle selection widget that shift adds at `src/ui.rs:1036` is the likely one.
Not tested: widgets inside a node body, which see the written modifiers for that frame.
Writing around `show` alone keeps the rest of the UI out of it.

### Driving the canvas through the egui MCP server

This is the recipe for E1's gates.

1. **Widget bounds on the canvas are in graph space.** The accessibility tree reports them without the layer transform: a title shown at (416, 292) reads as (242, 40). A locator such as `content_contains` therefore clicks the wrong place on any node. Use raw `pos` from `screen = scale * graph + translation`.
2. **Expose the transform and the pins.** A `SnarlPin` receives its rectangle in `draw`, and the scratch canvas records it in egui memory (`RecordedPin`). The readouts then print each pin in screen points, as "Pin n5 out 0: 573.2 461.7".
3. **To drag a wire under a zoom:** zoom with `scroll` at a canvas position, with `modifiers: { command: true }`. The zoom runs for several frames and the transform drifts (0.376 to 0.373 here), so wait a few frames before reading the pins. Then `drag` with raw `start` and `end` at the two pins' screen positions. A pin's hit rectangle scales with the zoom and is about 2 points wide at the minimum scale of 0.2, so frame first if a drag misses.
4. **`click` and `drag` modifiers do not reach the canvas.** The server puts them on the event, and egui-snarl reads `InputState::modifiers`, which only `Event::ModifiersChanged` sets. A shift-drag pans the canvas instead of selecting. The `scroll` modifier works. E1 needs a dev toggle like Hold shift, and has to write the value back when the toggle goes off, since the input state keeps modifiers between frames.
5. **Double-clicks are unreliable straight after a layout change.** A double-click on the background centres the graph, and it missed twice in a batch straight after closing tabs. Use a framing request to get a known transform.
6. **After a restart of the app, call `disconnect` before `attach`.** Otherwise the server reports it is already connected.

Screenshots worked throughout, as the screen stayed unlocked.

### Recommendation: adopt

Adopt egui-snarl 0.12.0 from crates.io for E1.

- Every item of the milestone works on the published crate with the viewer API alone. Frame cost has room at several times the plan's largest pass.
- Traps 2, 3, 4 and 8 have workarounds of a few lines, and the tests above catch a change to the egui-snarl behaviour behind them.
- A fork has a real cost here. henad-app is published on crates.io, so its dependency has to be published too: a fork means a ninth or tenth crate to release, or a vendored module, and every upstream egui bump to carry.
- Plain-click selection needs no fork, as "Plain-click selection" above shows. Whether E1 uses it is a point of UX for the maintainer.
- The one gap with no workaround is that pasted nodes or a Select all cannot start selected. E1's gates need neither.

A fork becomes the better choice only if the maintainer wants nodes to start selected.
The patch would be small, a public setter beside `get_selected_nodes`.
Proposing that setter upstream first is an option that needs the maintainer's decision.

### Decisions made on the maintainer's behalf

- The dev flag is the Cargo feature `snarl-spike` on henad-app, with a checkbox in the Editor tab's header. A new dock tab would have added a `Tab` variant for code that E1 deletes.

- Commands queue during `show` and run after it. A viewer callback never edits the `Snarl`.

- No CHANGELOG line, since no default build changes. The feature goes away with E1.

### What the review found

A review of this milestone found four things, all fixed in this record or the canvas.

- The record missed the panic of trap 8 on the undo route it prescribes. The review reproduced it on a standalone crate, and the tests above port it.
- The record said settable selection had no workaround for plain click, and that plain click would flip adopt to fork. Both claims were wrong, and the recommendation to adopt now stands more firmly. ## Issues found & future directions

- `a_location_survives_a_panic_on_a_rayon_worker` is flaky here and needs its own look. Several workers panic at once in that test, which is a likely cause, though no cause was confirmed.
- E1 replaces `scratch.rs`, and should port the tests that pin egui-snarl's behaviour along with the document and command layer.
- The maintainer decides whether a plain click selects, which the modifier write allows either way. Only a decision that pasted nodes or a Select all start selected would change the adopt recommendation.
- Snapshot undo has to apply a diff to the live `Snarl`. Rebuilding under one id misplaces the selection.
- E1's undo, and any other edit that can run with no pointer, needs the guard of trap 8. Without it, a keyboard undo during a wire drag ends the process.
- Not exercised: floating the Editor tab into its own window, a region dragged as a whole (E2 has to apply a body's delta to its members, and `get_node_info_mut` makes that possible), and a real pointer drag on a touch screen.
- Moving a region half into another region was left out of the spike. The frames nest correctly when the document says so, and E2 adds the gesture with its cycle check.
- A node's header reserves `header_drag_space` of blank space on its left, visible in the screenshots. E1 can set it to zero. The default grid pattern also reads bright at scale 1.0.
