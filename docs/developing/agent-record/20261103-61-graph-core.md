# Graph core, milestone G1 of the node editor

> G1 is the first milestone of the plan for GPU node models.
> It adds henad-graph, the crate that holds a graph model as data: its file format, its checker, its node catalogue, its host evaluator and its edit commands.
> `ModelFile` now dispatches on the file's `kind`, the command line reads and checks graph files, and the facade exposes the crate as `henad::graph`.
> Every grid file of the corpus seeds the same cells at tick 0 as the stock model it ports.
> The opening gate, PractRand over the draw lattice, failed both hash core candidates, so the draws use a provisional core until the maintainer chooses one.
> No graph runs yet: the WGSL compiler is G2.

### The opening gate: PractRand over the draw lattice

A draw of a graph model is a pure function of a key word, an element, a tick, an iteration and a sub-draw.
The plan picks the hash core between two candidates, `pcg4d` and a reduced chain of `pcg_hash`, by PractRand over that lattice in row and Morton order, and stops for the maintainer when both fail.

**Both failed.**
`pcg4d` as specified passed none of the 14 walks, each failing by 128 to 256 MB with 94 to 331 FAIL lines (FPF, BCFN, Gap-16, DC6, TMFn).
The literal chain `pcg_hash(k ^ pcg_hash(e ^ pcg_hash(t)))` passed 3 of 14.
A tuned chain, `chainm`, passed 6 of 14.
A control, SplitMix64 through the same pipe, reached 65 GB with no anomaly in 764 results, and a Python twin of `pcg4d` matched the driver's first eight words, so the `pcg4d` failures come from the core and not from the driver.

The draws used `chainm` provisionally, and nothing of library 1 is frozen on it.
`chainm` multiplies `e` and `i` by the odd constant `0x9E3779B1` before the XOR, which is an addition of the gate run, not part of design section 9.2:

```text
base = pcg_hash(k ^ pcg_hash(e * 0x9E3779B1 ^ pcg_hash(t)))     // pcg_hash(t) hoists per pass
r    = in_region ? pcg_hash(base ^ i * 0x9E3779B1) : base       // base hoists per element
word = s == 0 ? r : pcg_hash(r ^ s)
```

The maintainer's three options:

1. `pcg4d2`, two `pcg4d` calls in sequence, a reference outside the two candidates. It is the only core that passed all 14 walks to the cap, at about 21 multiplies per four words and 18 for one word.
2. `chainm` at about 5 multiplies per draw, accepting that it fails every region, sub-draw and multi-key walk.
3. Another core.

`chainm`'s failing walks include uses the design relies on: an iteration in a region (`row-n16-i8` at 512 MB, `row-n12-i16` at 16 GB), the second and fourth words of a point (256 MB) and several keys per element (256 to 512 MB).
The cause of the chain failures is inferred and not proved.
Every word of a point passes through one 32-bit value, so the words of one lattice point stay on a subset of 2^32 pairs, which BDayS2 detects as repeats.
For the literal chain, whole rows can repeat as XOR-shifted copies when `pcg_hash(t1) ^ pcg_hash(t2) < N`.
Nobody has measured what these failures do to a model's results.

`crates/henad-compute/src/gpu/runtime_grid/template.rs:175` keys the streams of runtime grid rules in the literal chain's form, and that chain's `row-n20` walk fails at 4 GB.
Nothing there was changed, and whether a current rule is affected is not known.

The cores:
- `pcg4d` is the JCGT function with input word `(i << 4) | (s >> 2)` and output word `s & 3`, so one call serves four sub-draws and the low nibble counts calls.
- `chain3` is the literal reduced chain above. `chain2` is `pcg_hash(pcg_hash(k ^ e) ^ t)`, the draft chain without its zero rounds, and `chain3e` is `pcg_hash(k ^ pcg_hash(t ^ pcg_hash(e)))`.
- `pcg4dw3` takes word 3 alone, one call per draw. `pcg4d2` is `pcg4d(pcg4d([k, e, t, (i << 4) | (s >> 2)]))[s & 3]`.

The walks:
- `row-nA`: tick outermost, then 2^A elements. `iB` adds 2^B iterations per element (`i8` is 8 iterations), and `sN` emits N sub-draws per point.
- `col-t16`: element outermost, 2^16 ticks per element.
- `keysM`: M keys per element, sequential, or (`rand`) derived through the key word.
- `morton-et`, `morton-eti`, `morton-keti`: Morton order over those words.
- Keys: `k0` is 0, `k1` is 1 and `kR` is `0x9E3779B9`.

Anomalies short of a FAIL: `pcg4d2` had no suspicious result and 8 "unusual" lines over its 14 walks, at p between about 1e-3 and 1e-5, on no consistent test and none repeated.
`chainm`'s passing walks had one "unusual" line, in `morton-keti-kR`.
`chainm` failed BDayS2 in the walks with several words per point, and FPF with BDayS2 in `row-n32`, at 2 GB, plausibly the limit of a 32-bit permutation (inferred).
`pcg4dw3` reached about 32 GB only on the 4D Morton walk before failing DC6 and others, which fits the published Morton-ordered BigCrush evidence covering neither row order nor fixed coordinates.

Static cost in `u32` multiplies, with `k`, `t` and `i` hoisted where possible and `pcg_hash` counted as 2: `chain3` 4 per draw, `chainm` 5 per draw plus 2 per further word and 3 per region iteration, `pcg4d` 6 for one word and 9 for four, `pcg4d2` 18 for one word and 21 for four.
No GPU timing was taken.

Limits of the run:
- A pass means no FAIL within 47 to 128 GB, far short of PractRand's usual 2^40 bytes or more. Longer runs were outside the cap.
- Each walk used one key apart from the two multi-key walks, so key dependence within a single-key walk was not swept.
- The first batch shared the machine with other builds (load average up to 82), so its byte counts are lower than an idle run would reach. The longest test took 1006 s, over 113 configurations at 12 at a time.

#### Procedure

PractRand is no CI dependency, and nothing of this procedure is in the repository but this record.

1. Download PractRand 0.96 from [SourceForge](https://sourceforge.net/projects/pracrand/files/PractRand_0.96.zip/download) (SHA-256 `e4caf7fda98b2c597bbda3b576753cf5a0f6047aab837c82be370ab798a672e1`) and unpack it.
2. On arm64, delete the `x86intrin.h` includes from `src/platform_specifics.cpp` and `tools/dummy_rng.h`, and make `high_resolution_time` return `std::chrono::high_resolution_clock::now().time_since_epoch().count()`. That function only feeds entropy to seeding, and no test code changes.
3. Build the library and the test program:

   ```bash
   c++ -std=c++14 -O3 -Iinclude -c src/*.cpp src/RNGs/*.cpp src/RNGs/other/*.cpp
   ar rcs PractRand.a *.o
   c++ -std=c++14 -O3 -Iinclude -Itools -pthread -o RNG_test tools/RNG_test.cpp PractRand.a
   ```

4. Save the driver below as `driver.rs` and build it with `rustc -O -C target-cpu=native -o driver driver.rs`.
5. Run each core and walk as one stream, `./driver CORE WALK KEY SUBS [A] [B] | ./RNG_test stdin64 -tf 2 -tlmax 1000s -tlfail`, with the arguments of the table below. `-tf 2` folds more widely and is more sensitive to low bits than the default, and `-tlfail` stops a stream at its first failing report. The gate ran 12 streams at a time.

??? note "The driver, `driver.rs`"

    ```rust
    // Standalone stream driver for the G1 PractRand gate. No link to Henad.
    // usage: driver CORE WALK KEY SUBS [A] [B]
    //   CORE: pcg4d | chain3 | chain2 | splitmix
    //   WALK: row N R | col T | keys N M | keysrand N M | mort2 | mort3 | mort4
    //   Writes little-endian u32 draws to stdout, in emission order.
    use std::io::{self, Write};

    #[inline(always)]
    fn pcg_hash(input: u32) -> u32 {
        let state = input.wrapping_mul(747796405).wrapping_add(2891336453);
        let word = ((state >> ((state >> 28) + 4)) ^ state).wrapping_mul(277803737);
        (word >> 22) ^ word
    }

    #[inline(always)]
    fn pcg4d(input: [u32; 4]) -> [u32; 4] {
        let mut v = input.map(|x| x.wrapping_mul(1664525).wrapping_add(1013904223));
        for round in 0..2 {
            v[0] = v[0].wrapping_add(v[1].wrapping_mul(v[3]));
            v[1] = v[1].wrapping_add(v[2].wrapping_mul(v[0]));
            v[2] = v[2].wrapping_add(v[0].wrapping_mul(v[1]));
            v[3] = v[3].wrapping_add(v[1].wrapping_mul(v[2]));
            if round == 0 {
                v = v.map(|x| x ^ (x >> 16));
            }
        }
        v
    }

    #[derive(Clone, Copy, PartialEq)]
    enum Core { Pcg4d, Pcg4dW3, Pcg4dXs, Pcg4d2, Chain3, Chain2, Chain3e, ChainM, SplitMix }

    struct Sink { buf: Vec<u8>, bytes: u64, smix: u64 }
    impl Sink {
        #[inline(always)]
        fn push(&mut self, w: u32) {
            self.buf.extend_from_slice(&w.to_le_bytes());
            if self.buf.len() >= 1 << 20 {
                if io::stdout().write_all(&self.buf).is_err() {
                    eprintln!("driver_bytes={}", self.bytes);
                    std::process::exit(0);
                }
                self.bytes += self.buf.len() as u64;
                self.buf.clear();
            }
        }
    }

    // Emits sub-draws 0..subs of one lattice point. `region` says whether the context holds an iteration word.
    #[inline(always)]
    fn point(core: Core, k: u32, e: u32, t: u32, i: u32, region: bool, subs: u32, out: &mut Sink) {
        match core {
            Core::Pcg4d => {
                let mut s = 0;
                while s < subs {
                    let v = pcg4d([k, e, t, (i << 4) | (s >> 2)]);
                    let mut w = 0;
                    while w < 4 && s < subs { out.push(v[w]); w += 1; s += 1; }
                }
            }
            // Word 3 alone, one call per draw. The nibble counts draws.
            Core::Pcg4dW3 => {
                for s in 0..subs { out.push(pcg4d([k, e, t, (i << 4) | s])[3]); }
            }
            // Four words per call with one more xorshift on the way out.
            Core::Pcg4dXs => {
                let mut s = 0;
                while s < subs {
                    let v = pcg4d([k, e, t, (i << 4) | (s >> 2)]).map(|x| x ^ (x >> 16));
                    let mut w = 0;
                    while w < 4 && s < subs { out.push(v[w]); w += 1; s += 1; }
                }
            }
            // Two full calls in sequence, four words per outer call. A reference, not a candidate.
            Core::Pcg4d2 => {
                let mut s = 0;
                while s < subs {
                    let v = pcg4d(pcg4d([k, e, t, (i << 4) | (s >> 2)]));
                    let mut w = 0;
                    while w < 4 && s < subs { out.push(v[w]); w += 1; s += 1; }
                }
            }
            Core::Chain3 | Core::Chain2 | Core::Chain3e | Core::ChainM => {
                const C: u32 = 0x9E3779B1;
                let base = match core {
                    Core::Chain3 => pcg_hash(k ^ pcg_hash(e ^ pcg_hash(t))),
                    Core::Chain2 => pcg_hash(pcg_hash(k ^ e) ^ t),
                    Core::Chain3e => pcg_hash(k ^ pcg_hash(t ^ pcg_hash(e))),
                    _ => pcg_hash(k ^ pcg_hash(e.wrapping_mul(C) ^ pcg_hash(t))),
                };
                let tweak = if core == Core::Chain3e || core == Core::ChainM { i.wrapping_mul(C) } else { i };
                let r = if region { pcg_hash(base ^ tweak) } else { base };
                out.push(r);
                for s in 1..subs { out.push(pcg_hash(r ^ s)); }
            }
            Core::SplitMix => {
                for _ in 0..subs {
                    out.smix = out.smix.wrapping_add(0x9E3779B97F4A7C15);
                    let mut z = out.smix;
                    z = (z ^ (z >> 30)).wrapping_mul(0xBF58476D1CE4E5B9);
                    z = (z ^ (z >> 27)).wrapping_mul(0x94D049BB133111EB);
                    out.push((z ^ (z >> 31)) as u32);
                }
            }
        }
    }

    // Collects every `dims`-th bit of `c`, starting at bit `shift`.
    #[inline(always)]
    fn compact(c: u64, dims: u32, shift: u32) -> u32 {
        let mut r = 0u64;
        let mut b = 0;
        while (b * dims + shift) < 64 && b < 32 {
            r |= ((c >> (b * dims + shift)) & 1) << b;
            b += 1;
        }
        r as u32
    }

    fn parse(s: &str) -> u64 {
        if let Some(h) = s.strip_prefix("0x") { u64::from_str_radix(h, 16).unwrap() }
        else if let Some(p) = s.strip_prefix("2^") { 1u64 << p.parse::<u32>().unwrap() }
        else { s.parse().unwrap() }
    }

    fn main() {
        let a: Vec<String> = std::env::args().collect();
        let core = match a[1].as_str() {
            "pcg4d" => Core::Pcg4d, "chain3" => Core::Chain3, "chain2" => Core::Chain2,
            "pcg4dw3" => Core::Pcg4dW3, "pcg4dxs" => Core::Pcg4dXs, "pcg4d2" => Core::Pcg4d2, "chain3e" => Core::Chain3e, "chainm" => Core::ChainM,
            "splitmix" => Core::SplitMix, other => panic!("core {other}"),
        };
        let walk = a[2].as_str();
        let k = parse(&a[3]) as u32;
        let subs = parse(&a[4]) as u32;
        let p = parse(a.get(5).map_or("0", |s| s));
        let q = parse(a.get(6).map_or("0", |s| s));
        let mut o = Sink { buf: Vec::with_capacity(1 << 21), bytes: 0, smix: 1 };
        match walk {
            // Tick outermost, then element, then iteration. R == 1 means no region.
            "row" => {
                let region = q > 1;
                let r = q.max(1);
                for t in 0u64.. { for e in 0..p { for i in 0..r {
                    point(core, k, e as u32, t as u32, i as u32, region, subs, &mut o);
                } } }
            }
            // Element outermost, so each element's series over `p` ticks stays contiguous.
            "col" => {
                for e in 0u64.. { for t in 0..p {
                    point(core, k, e as u32, t as u32, 0, false, subs, &mut o);
                } }
            }
            // Each element draws under `q` keys in turn. Sequential keys, or keys through the design's key word.
            "keys" | "keysrand" => {
                let keys: Vec<u32> = (0..q as u32).map(|j| {
                    if walk == "keys" { k.wrapping_add(j) }
                    else { pcg_hash(pcg_hash(pcg_hash(j).wrapping_mul(2654435761) ^ pcg_hash(1)) ^ k) }
                }).collect();
                for t in 0u64.. { for e in 0..p { for &key in &keys {
                    point(core, key, e as u32, t as u32, 0, false, subs, &mut o);
                } } }
            }
            "mort2" => for c in 0u64.. {
                point(core, k, compact(c, 2, 0), compact(c, 2, 1), 0, false, subs, &mut o);
            },
            "mort3" => for c in 0u64.. {
                point(core, k, compact(c, 3, 0), compact(c, 3, 1), compact(c, 3, 2) & 0xFFFF, true, subs, &mut o);
            },
            "mort4" => for c in 0u64.. {
                point(core, k.wrapping_add(compact(c, 4, 0)), compact(c, 4, 1), compact(c, 4, 2),
                      compact(c, 4, 3) & 0xFFFF, true, subs, &mut o);
            },
            other => panic!("walk {other}"),
        }
    }
    ```

### henad-graph

henad-graph sits on henad-core and henad-compute, outside egui, and publishes as the ninth crate.
It is in the root `Cargo.toml`, the wasm32 lines of `check.sh` and CI, the patch list of the `downstream` job, the publish order in `releasing.md`, the crate graph in `AGENTS.md`, and its own topic file, `agents/henad-graph.md`.
It sets `#![warn(missing_docs)]` and `#![recursion_limit = "256"]`, and its public types implement `Debug`.

- **File format.** A graph file is `format = "henad-model"`, `format_version = 1`, `kind = "graph"`, a `[graph]` table with the topology and `library = 1`, one `[[target]]` with `backend = "gpu"`, a world table, declarations, a stack of passes holding nodes, functions and a trailing `[editor]` region. The reader records the place of every table and key, and refuses an `apply` key and every other key it does not know. The canonical writer writes one text per graph, `runs = []` included, and no optional key without a default. The canonical text before `[editor]` is the code identity, in the format `henad-graph/1`, so moving a node leaves it alone.
- **Checker.** Every rule a grid can meet, every failure reported at once. A node that fails to type yields a hole, so one bad wire gives one diagnostic. Each diagnostic of a node carries its pass and node id, and the checker warns of unreached nodes and of a Repeat whose `count` can pass `max`. Cost sums bottom-up with saturating arithmetic, and no step recurses on a hostile file.
- **Catalogue.** The 64 kinds G1's row of the plan names, each a static definition with a signature, semantics, cost, parity and known-answer cases, `cat.transition` with two rules in one phase and with two phases among them. `library.lock` holds one line per definition and per limit, and its test fails on a kind without cases. The test prints the "Used by" cells and a coverage line from the corpus: 27 of 64 kinds appear in it.
- **Draws** (`draw.rs`). The key word, the phase words, the tick word and the mixed-radix iteration word, on the provisional `chainm`. The first step of G2 moved them to `pcg4d2`, below.
- **`region.repeat`**, with its accumulators, its clamp and its cost of `1 + max * (body cost + 1)`.
- **Host evaluator** (`host/`). It runs init passes and action reruns on the CPU, one element at a time in index order, and uploads the lanes they write. A pass reads its start and commits at its end. A file that checks never panics it, and the mutation test runs it on every edited file that checks.
- **Edit commands** (`edit/`). `GraphBuilder` runs `EditCommand`s on a copy, so a refused command changes nothing, and renames rewrite every reference.
- **Starters.** `game_of_life`, `vote` and `sir` in `starters/`, each ported to one GPU target with a `node_<model>` id and no `apply` key, embedded with `include_str!` and returned by `starters()`. Game of Life's Randomise uses the press-seed form of nine nodes, as the stock `randomise.wgsl` does. The exact port of `gpu_sir`, `gpu_sir_exact.toml`, sits in henad-models' `tests/fixtures/graphs/`.
- **Diagnostics.** `DiagnosticSeverity::Warning`, and `CodeDiagnostic` gains an optional pass and node id.

### Model files over kinds

`ModelFile` in henad-explore is an enum: `GpuGrid(Box<GridRuleFile>)` and `Graph(Box<GraphFile>)`.
`GridRuleFile` is the former struct, and a grid rule's file behaves as before, its tests unchanged but for reading `rule()` as an `Option`.
`ModelFile::parse` reads the header and dispatches on `kind`, and an unknown kind names both kinds this build reads.
A graph's `entry` returns the checker's errors as `ModelFileError::Graph`, then the host evaluator's, then `ModelFileError::Unsupported`, since no graph runs before G2.
`warnings` returns the graph checker's warnings.
The facade exposes henad-graph as `henad::graph` behind `model-files`.

### `--model-file` reads graphs

henad-cli prints a graph file's warnings to stderr and its errors at `path:line:column`, each with a note naming its pass and node:

```text
broken.toml:123:6: error: node n12 uses 'grid.lifelike', which this build has no definition of
  note: in node n12 of pass 'step'
```

A graph that checks is refused with `the graph checks, but this build cannot run graph models yet`, placed at the header's `id`, exit 1.

### Gate tests in henad-models

`src/tests/graph_corpus.rs` sits beside `runtime_parity.rs`.
henad-models takes henad-explore with `model-files` and henad-graph as a path-only dev-dependency.

### Decisions made on the maintainer's behalf

- `ModelFile`'s variants are both boxed, for clippy's `large_enum_variant`, and the enum is `#[non_exhaustive]`.
- `ModelFile::parse` refused a file past 1 MiB, henad-graph's `MAX_FILE_BYTES`, before reading the header, whatever its kind. The review undid this (below): only a graph is held to the limit.
- A graph's `entry` also runs `HostEvaluator::new`, so an init pass the host cannot run is reported now instead of at G2's build.
- The CLI adds a graph diagnostic's pass and node as a note, since `CodeDiagnostic`'s `Display` prints neither.
- henad-models takes henad-graph as a path-only dev-dependency. The plan expected none, but henad-explore does not re-export henad-graph, and the host evaluator is reached only through it. The edge runs against no normal edge and stays out of the package.

One finding is left for G2, as the review proposed.
Host init has no bound on its work and no cancel.
One init `region.repeat` of cost 64003 per element took 2.73 s at 128 by 128 in a release build, which is about 3 minutes at the starters' 1024 by 1024 and about 13 hours at 16384 by 16384, on one thread.

## Issues found & future directions

- **The hash core.** The maintainer chooses between `pcg4d2`, `chainm` and another core. The `rand.*` cases and their lock lines move with the choice, and library 1 must not freeze before it.
  Since the first step of G2 the draws use `pcg4d2` provisionally, the only core that passed every walk: `pcg4d(pcg4d([k, e, t, (i << 4) | (s >> 2)]))[s & 3]`, with `i` 0 outside every region. `draw_core` in `draw.rs` holds it as one function, and so does its WGSL twin in `draw.wgsl` since the second step of G2, so another core is one edit on each side plus the `rand.*` case words and their three lock lines.
- **`schema_hash` reads the model id.** The plan says it does not, and relies on that for G2's and A2's gate "Schema hashes equal the stock models'". `henad_core::explore::fingerprint::schema_hash` writes `schema.id` first, so a `node_<model>` entry never hashes like its stock model. The test holds every other part of the schema equal under the stock id and asserts that the ids make the hashes differ. The maintainer decides whether the gate means this, or whether the hash should drop the id, which would change every recorded hash.
- **What G2 must connect.**
  - A `ModelEntry` for a graph from `ModelFile::entry`, replacing `ModelFileError::Unsupported`, with the schema `graph_corpus.rs` builds: `grid_width` and `grid_height` from 1 to 16384 at the `[grid]` defaults, then the file's parameters, stats and actions.
  - `seed_buffers` through `HostEvaluator::init(HostWorld::Grid { width, height, boundary }, &params[2..], seed)` and `lanes.column(id).words()` per buffer, narrowed to each lane's storage.
  - Action reruns through `HostEvaluator::rerun` on an action stream started at `action_seed(seed)`.
  - WGSL forms of every G1 kind run against the same known-answer case files, through `case_files.rs`.
  - The draw words of `draw.rs` exactly, with `key_word` computed on the host and passed in the uniform block.
  - henad-cli then runs a graph file through the same path, and its test of a refused graph becomes a test of a run.
  - The second step of G2 connected all of these. A lane's storage stays one word per element on the device, since `storage` is read by a CPU target alone, and five cases over `u64` or `f64` became `CaseScope::Host`.
- **The own-cell `at`.** The writer rule that leaves the own-cell `at` unwritten belongs to `lane.get_at`, an A2 kind. Nothing in G1 writes an `at`.
- **The literal chain in runtime grid rules.** The runtime grid template keys streams in the literal chain's form, which failed `row-n20` at 4 GB. Whether a current rule is affected is not known.
- **Host init work.** G2's `Demand` should count the `cost * elements` of the init and rerun passes against a host budget, or `HostEvaluator::init` should take a cancel, so Build and the preview refuse or abort a file whose init would stall the build thread. The review measured the rate above.
- **The canonical size limit.** At about 116 bytes of canonical text per node, a realistic file reaches 1 MiB near 9000 nodes, below `MAX_NODES_IN_FILE` (16384). The maintainer may raise `MAX_FILE_BYTES`, which moves its lock line.
- **Coverage.** 37 of 64 kinds appear in no corpus file. Library 1 allows that for general-purpose kinds, and their known-answer cases hold them.
